## 2. 真实流水线测试（合成语音）

测试音频由 Windows SAPI 中文语音（Microsoft Huihui）合成 14 轮对话，两位说话人用不同音高区分，
总时长 **2 分 46 秒**。**这是合成语音，只用于验证流水线是否跑通，不能代表真实访谈的识别准确率。**

命令：`python tools/e2e_run.py`（真实 WhisperX，medium / int8 / 8 线程 / beam 5 / batch 8）

| 指标 | 结果 |
| --- | --- |
| 模型加载 | 9.1 s |
| 转码 + 静音分析 | < 1 s |
| 语音识别 | 49.8 s（6 个 VAD 片段） |
| 全流程 | 61.2 s |
| 实时率 RTF | **0.30–0.37**（约为录音时长的 1/3） |
| 时间戳 | 单调递增，首段 0.93 s |
| 与脚本原文的字符相似度 | 0.893 |

识别错误示例（未做任何自动修改，保持机器原样）：

| 原文 | 识别 |
| --- | --- |
| 掉毛 | 吊毛 |
| ，（全角逗号） | ,（半角逗号） |
| 二十 / 两千 / 三千 | 20 / 2000 / 3000 |

结论：CPU 转录链路可用，速度约为实时的 3 倍（medium 模型）。中文同音字错误属模型能力问题，
应用不自动改写，只在界面上标记低置信度片段供人工校对。

### 2.1 medium 与 large-v3 对比（同一样本、同机实测）

命令：`python tools/model_bench.py --model medium` / `--model large-v3`（结果追加写入 `logs/model_bench.txt`）。
两次测量都在同一台机器、同一段 2:46 合成音频、int8、8 线程、beam 5、batch 8 下完成，
测量时后台还开着本应用的服务进程，因此耗时略高于理想空载值。

| 指标 | medium | large-v3 |
| --- | --- | --- |
| 模型加载（权重已缓存） | 14.6 s | 20.1 s |
| 模型加载（首次，含 HF 下载与 int8 转换） | — | 190.6 s |
| 转写 2:46 样本 | 77.3 s（RTF 0.47） | 106.9 s / 137.5 s（RTF 0.64 / 0.83） |
| 常驻内存（int8） | 1.3 GB | 2.1 GB（加载峰值 3.7 GB） |
| 磁盘占用（`models/whisper` 内权重） | 1.46 GB | 2.95 GB |
| 识别结果 | 6 段 / 338 字 | 6 段 / 333 字 |

观察：

1. **速度**：large-v3 约为 medium 的 1.4–1.8 倍耗时（两次测量有波动，因为服务进程在同时运行）。
   按此折算，38 分钟访谈的语音识别需要约 **25–35 分钟**（medium 实测 1130.9 s ≈ 19 分钟）。
2. **质量**：同一句 medium 输出「吊毛」、large-v3 输出「掉毛」（正确）。但样本是 TTS 合成语音，
   只有这一处差异，**不足以得出准确率结论**；真实录音的收益需要你自己对比。
3. **换模型会让已有分段缓存失效**：`asr/chunks` 的缓存键包含模型名，
   切换到 large-v3 后必须整段重新转录，旧逐字稿在校验前不会被覆盖。

### 2.2 强制对齐（词级时间戳）实测代价

命令：`python tools/align_bench.py`（复用项目 `20261103-113838-6baa9f` 已缓存的 6 段识别结果，
只跑 `whisperx.align`，结果写入 `logs/align_bench.txt`）

| 项目 | 结果 |
| --- | --- |
| 对齐模型 | `jonatasgrosman/wav2vec2-large-xlsr-53-chinese-zh-cn`（wav2vec2-large，CTC） |
| 首次下载 | 1.28 GB ×2（仓库同时含 `.bin` 与 `.safetensors`，实测占 **2.55 GB** 磁盘） |
| 对齐耗时（模型已缓存） | 80.8 s / 164.4 s 音频 = **0.49× 实时** |
| 产出 | 338 个字级时间戳（中文按字），每个带 `score` 置信度 |
| 段边界位移 | 平均 0.27 s，最大 2.86 s |

对 38 分钟录音的推算：对齐本身约多花 **19 分钟**（0.49× 实时），且当前实现按分段重新加载
对齐模型（每次约 5–8 s）。

真实项目实测（38:15 双人访谈，`POST /api/projects/{id}/align`，只补时间戳不重新识别）：

| 项目 | 结果 |
| --- | --- |
| 对齐耗时 | **508.4 s / 2295 s 音频（0.22× 实时）** |
| 输出 | 4 个分段全部生成词级时间戳（81 个 ASR 段均带 `words`） |
| 逐字稿 | 254 段 → 273 段，切分点全部落在真实字边界 |
| 含两位说话人的 utterance | 2 / 254 → **0 / 273**（按分离时间轴核对） |

切分点误差的量化（`tools/diag_align_ab.py`，第 0 个 10 分钟分段，1841 字）：
按字符比例切时，**230 字（12.5%）落在“另一个说话人”的行里**，受影响分段 20/21。
典型例子：25.1 s 处“两只猫多大了”这句提问被切进了受访人的答句。
补上词级时间戳后，同样的核对口径下该比例降为 0。

仍需注意：对齐只能修正“切到哪里”，不能修正“这段到底是谁说的”。
例如同一项目 25.14–25.97 s 的分离结果把提问判给了 SPEAKER_00，
对齐后这句话仍然会跟随错误标签（但至少整段文本是完整的，可以用下拉框一键改归属）。

对齐产出的时间戳还有一类缺陷：当 ASR 分段远长于文本时，wav2vec2 会把某个字
「撑」到后面的静音里。实测 7089 个字级时间戳中 **521 个（7.3%）超过 0.8 s，最长 16.65 s**。
因此 `merge.py` 会把超过 1 s 的字收窄到实际语音区间（取离上一个字最近的那一段），
避免一个字横跨多名说话人的片段。修正后同一项目逐字稿 273 段 → 258 段（15 行归属变化）。

作用范围（重要）：

- **改善**：说话人切换处的切分点（有词级时间就切在字边界，否则按字符比例切，可能把半句
  话分给另一个人）；`low_confidence` 标记（它依赖 word `score`，**不开对齐时该标记永远不会
  出现**）；点击时间戳的定位精度。
- **不改善**：识别出的文字本身、同音字、标点、整段的时间轴偏移。

### 2.3 二次声纹校验（纠正整段判错人）

pyannote 会偶发地把两个人对调几秒。做法：对每个 ≥0.6 s 的 turn 用
`pyannote/wespeaker-voxceleb-resnet34-LM` 提 256 维声纹，全局 k-means 重新聚类，
只在声纹相似度收益 > 0.05 时才翻转标签（保守策略）。

| 项目 | 结果 |
| --- | --- |
| 命令 | `POST /api/projects/{id}/refine`（或界面「二次声纹校验（纠正归属）」） |
| 耗时（38:15，916 个 turn） | **51.5 s**，不重新识别、不重跑分离 |
| 翻转 | **48 / 916 个 turn**（保守跳过若干低置信度的） |
| 备份 | 原结果写入 `diarization/raw.before_refine.json` |

同一段（12–36 s）的前后对比（`tools/compare_refine.py`）：

| | 逐字稿 |
| --- | --- |
| 校验前 | `[16.42-26.02] 受访人: …右边一只两只猫多大了两只` / `[26.02-33.13] 采访人: 都是六岁七岁左右吧…` |
| 校验后 | `[16.42-20.89] 受访人: …右边一只` / `[22.02-23.36] 采访人: 两只猫` / `[23.36-28.36] 受访人: 多大了两只都是六岁七岁左右吧` / `[29.30-33.13] 采访人: 那其实挺久挺大了…` |

回答被改回了受访人（原本错在采访人），提问的开头也回到了采访人；残留的 `多大了`
因为和回答落在同一个 turn 内，仍需手动拆行。

另测：`pyannote/speaker-diarization-3.1` 与本机默认的 Community-1 在这段音频上
**输出逐 turn 一致**（0–300 s：119 vs 120 个 turn，边界精确到 0.01 s 相同）——
两者的 segmentation 是同一套权重，2 人固定时聚类差异不改变结果，所以换 3.1 不能修复归属。

## 3. 说话人分离

已用**真实模型**跑通（`pyannote/speaker-diarization-community-1`，CPU）：

| 项目 | 结果 |
| --- | --- |
| 样本 | 中文双人合成访谈前 40 秒（16 kHz 单声道） |
| 模型加载 | 11.7 s（含首次 HF 下载后的本地加载） |
| 分离耗时 | 13.7 s，约 **0.34× 实时** |
| 输出 | 8 个 turn，识别出 2 位说话人（SPEAKER_00 / SPEAKER_01） |

真实录音长跑（用户提供的 38:15 双人访谈，固定 2 人）：

| 项目 | 结果 |
| --- | --- |
| 分离耗时 | **2115.8 s（约 0.92× 实时）** |
| 输出 | 2 位说话人，187 段中 95 / 92 段均衡分布 |
| 合并后 | 逐字稿 187 段，其中 90 段标记「说话人不确定」（短句 + 边界切分导致） |

过程中修复了两个真实问题：

1. **403 gated**：token 有效（账号 KagamiZhang），但未在
   <https://huggingface.co/pyannote/speaker-diarization-community-1> 接受条款 →
   模型列表里没有该账号。现已在设置页提供「验证 Token 与模型授权」按钮，能直接区分
   `missing / invalid / network / gated`，不再只把错误写进日志。
2. **`TypeError: device must be an instance of torch.device, got str`**：
   pyannote 4 的 `Pipeline.to()` 不接受字符串。已改为 `torch.device("cpu")`，
   并加了回归测试（`tests/test_diarization.py`）。

其它已验证：`Pipeline.from_pretrained(token=..., cache_dir=...)` 签名、
`Pipeline.__call__(file, num_speakers=..., hook=...)`、以
`{"waveform": tensor[1,N], "sample_rate": 16000}` 传入以绕开 torchcodec、
`output.speaker_diarization.itertracks(yield_label=True)` 解析、
以及合并逻辑（`tests/test_merge.py`、`tests/test_pipeline_integration.py`）。

**仍需你自己评估**：真实录音里的短插话、重叠语音、音色相近的说话人；建议先跑一段
双人访谈，核对 A/B 归属与时间轴，再决定是否启用「固定 2 人」。合成音频用的是同一
音色变调，聚类难度与真人不同，不能作为准确率结论。

## 4. 本地大模型纪要

### 4.1 速度基线

`qwen3:8b` (Q4_K_M) 在本机（Ollama 自动选用 6 线程）的实测：

| 指标 | 结果 |
| --- | --- |
| 生成速度 | **3.4–3.8 token/s** |
| 首段 prompt | 825 tokens |
| 模型加载 | 8.6 s |

> 需要更快迭代时可在 Ollama 中改用 `qwen3:4b` / `qwen3:1.7b`，应用支持任意本地模型。

### 4.2 端到端纪要（真实生成）
同一段 2:46 合成访谈，通过网页「AI 纪要」生成（模板 = 定性研究访谈纪要，模型 = qwen3:8b，
逐字稿来源 = 人工校对版）：

| 指标 | 结果 |
| --- | --- |
| 分段数 | 1（402 字） |
| 事实抽取（map） | 172.7 s，11 条事实 |
| 合并 | 单段跳过 LLM 合并，改用确定性去重 |
| 撰写纪要（compose） | 374.5 s（约 1400 字输出） |
| 依据核查（verify） | 154 s |
| 全流程 | **701.5 s（约 11.7 分钟）** |
| 核查结论 | `ok`，0 条无依据陈述 |

生成结果（节选，完整见 `projects/<id>/summary/final.md`）：

```markdown
## 3. 受访者背景信息
- 年龄：29岁 [00:00:01]
- 职业：产品设计 [00:00:01]
- 居住地：杭州 [00:00:01]

## 5. 主要痛点和困难
- 挪威森林猫掉毛严重，每天都要吸地 [00:01:04]
- 手持吸尘器续航不足，仅20分钟 [00:01:04]

## 8. 产品偏好与未满足需求
- 未提及具体品牌或型号 [原文未提及]

## 9. 价格接受度
- 价格在2000元以内可以接受 [00:01:04]

## 11. 潜在需求假设
- 可能需要一款续航时间更长的吸尘器，以满足日常清洁需求 [依据：00:01:04]
```

观察：

- 12 个章节与需求一致，结论均带时间戳，价格数字（2000）与原文一致；
- 「潜在需求假设」标注为推论并给出依据，未混入事实；
- 原文没有的信息（品牌、其他功能偏好）明确写「原文未提及」，没有编造；
- 生成时使用的是**人工校对版**逐字稿（`source=edited`），证明校对版优先；
- 早先的两次运行中，8B 模型曾把价格写进「产品偏好」、把第 9 节误写成「原文未提及」，
  已通过提示词硬约束修正（存在 price 事实时必须写出）；「依据核查」也曾把同义改写误判为
  「表述更强」，已收紧为只报四类严重问题（编造 / 数字不符 / 推论写成事实 / 否定颠倒）。

局限：8B 模型在单次运行中仍可能给出不完美的章节归类（如上例第 8 节），需要人工复核。

### 4.3 长文本（多分段）验证状态
